1. Overview

Structured Field Values are a syntax for HTTP header and trailer values, defined by RFC 9651. Headers such as Priority, Accept-CH, and Sec-CH-UA use this syntax. It defines a small closed set of data types (integers, decimals, strings, tokens, byte sequences, booleans, dates, and display strings) and three containers (items, lists, and dictionaries), each with an exact, deterministic parsing and serialization algorithm.

gauge15 implements that algorithm directly against the RFC text, section by section, with no dependencies beyond the C++ standard library. It is a parser and serializer only. It does not open sockets, does not know what a request or a response is, and has no opinion about which HTTP library sits in front of it.

2. Scope

RFC 9651 obsoletes RFC 8941. The two differ by two data types, Date and Display String, added in 9651. gauge15 targets 9651, since a 9651-conformant parser reads everything a 8941-conformant one does, and the reverse is not true.

The library does not implement RFC 9110's field-line-combining step (joining repeated header instances with ", ") or byte-to-ASCII conversion. Both are the caller's responsibility, since both depend on the transport the caller is using and neither is specific to Structured Fields.

3. Data model

Eight bare item types, per RFC 9651 §3.3:

TypeC++ representationWire example
Integerint64_t42
Decimalsfv::Decimal4.5
Stringstd::string"hello"
Tokensfv::Tokengzip
Byte Sequencesfv::ByteSequence:cHJldGVuZA==:
Booleanbool?1
Datesfv::Date@1659578233
Display Stringsfv::DisplayString%"caf%c3%a9"

A bare item plus its parameters forms an Item. An ordered sequence of items with its own parameters forms an InnerList. A List is a sequence of items and inner lists. A Dictionary is an ordered, unique-keyed mapping from strings to items or inner lists, where re-assigning an existing key overwrites its value in place rather than moving it to the end of the sequence.

Token is a distinct wrapper type rather than reused std::string, since a Structured Field parser must keep tokens and strings distinguishable, and C++ has no native type for one that does not also fit the other.

4. Interface

Four functions cover the whole public surface:

sfv::Result<sfv::Item>       sfv::parse_item(std::string_view);
sfv::Result<sfv::List>       sfv::parse_list(std::string_view);
sfv::Result<sfv::Dictionary> sfv::parse_dictionary(std::string_view);

sfv::Result<std::string>     sfv::serialize(const sfv::Item&);
sfv::Result<std::string>     sfv::serialize(const sfv::List&);
sfv::Result<std::string>     sfv::serialize(const sfv::Dictionary&);

Result<T> holds either a value or an Error (a message and a byte offset). RFC 9651 §1.1 states that parse failure is the field's only defined error behaviour, a normal outcome rather than an exceptional one, so the library returns it rather than throwing.

Everything under sfv::detail:: is the implementation these four functions are assembled from: one function per RFC subsection, named to match it (detail::parse_integer_or_decimal is §4.2.4, detail::serialize_dictionary is §4.1.2, and so on). It is reachable, for anyone who needs a single container's algorithm in isolation, but is not the intended entry point.

5. Examples

Item, with a parameter

auto r = sfv::parse_item("42;foo=?1");
// r.value().value  == sfv::BareItem{int64_t{42}}
// r.value().params == {"foo": true}

sfv::serialize(r.value()).value();
// "42;foo"   -- Boolean true parameters omit their value on output

List, with an inner list

auto r = sfv::parse_list("sugar, tea, (\"milk\" \"honey\");source=farm");
// r.value()[0], r.value()[1] : Item      (Token "sugar", Token "tea")
// r.value()[2]               : InnerList (String "milk", String "honey"),
//                               params = {"source": Token "farm"}

Dictionary, with the boolean shorthand

auto r = sfv::parse_dictionary("u=1, a=?0, c");
// r.value().get("u") -> Item{int64_t{1}, {}}
// r.value().get("c") -> Item{true, {}}       -- bare key means true

sfv::serialize(r.value()).value();
// "u=1, a=?0, c"

6. Design notes

Decimal is fixed-point

sfv::Decimal stores its value as an int64_t scaled by 1000, not as double. RFC 9651's Decimal is defined with an exact three-digit fractional limit and round-trips exactly; IEEE 754 binary64 cannot represent many such values exactly, 0.1 among them. The fixed-point representation has no such gap.

Ordered map, not std::map

Parameters and Dictionary are both specified as ordered maps with unique keys, where re-setting an existing key overwrites its value without changing its position. Neither std::map nor std::unordered_map preserve that property, so the library defines its own, backed by a flat vector, which is also the faster choice at the sizes these containers actually reach in practice.

Self-rolled base64 and UTF-8

Byte Sequence needs base64; Display String needs UTF-8 validation strict enough to reject overlong encodings and surrogate code points, not merely to decode well-formed input. Both are implemented directly rather than pulled in as dependencies, keeping the library at zero dependencies beyond the standard library.

Single header

The distributed form is one generated file, produced from the real multi-file source by a small script that concatenates every header in dependency order and merges the include guards. It is not hand-maintained, and is verified against the same conformance suite as the source it is generated from before being committed.

7. Conformance and testing

Tested against the community-maintained structured-field-tests suite named in RFC 9651 Appendix B: 1,395 checks, covering every data type and container the RFC defines, passing identically under GCC 13 and Clang 18 with zero warnings under -Wall -Wextra -Wpedantic -Wconversion -Wshadow -Wsign-conversion.

Fuzzed with libFuzzer against all three top-level parse functions, seeded from every value in the conformance suite: 10,027,412 executions, zero crashes, checking both crash-freedom and that parse–serialize–reparse round-trips to an equal value.

Neither of these is a claim of completeness. They are what has actually been checked, stated exactly, not rounded up.

8. Building

# single file, drop into any project
#include "gauge15/sfv.hpp"

# or, from source
mkdir build && cd build && cmake .. && make && ctest

C++20 required for structured bindings over OrderedMap iteration and if constexpr in the bare-item visitor. No third-party dependency, at any point, in the library itself.
